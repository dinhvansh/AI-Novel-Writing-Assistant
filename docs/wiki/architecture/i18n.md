# i18n Architecture (Vietnamese Localization)

## Background

This repository was forked from a Chinese-language upstream. The single
maintainer of the fork uses the application as a personal internal tool
in Vietnamese. Translating the codebase by editing inline string literals
would have made future upstream merges destructive. We therefore route
every user-visible string through an i18n layer that resolves at runtime.

The same architecture also separates concerns cleanly between
`docs/wiki/prompts/output-language-directive.md` (AI-generated content
language) and the React/Express UI copy translation handled here.

## Decision

We adopt the standard `i18next` ecosystem on both client and server:

| Layer  | Library                         | Version pin |
|--------|---------------------------------|-------------|
| Client | `i18next` + `react-i18next`     | `^23.16.0` + `^15.2.0` |
| Client | `i18next-icu` (plural / select) | `^2.3.0`   |
| Server | `i18next` + `i18next-icu`       | `^23.16.0` + `^2.3.0` |
| Tooling| `i18next-parser`, `fast-check`  | `^9.0.0`, `^3.23.0` |

Locale bundles are eager-imported as JSON modules from
`@ai-novel/shared/localization/locales/*.json` so they are bundled by
Vite at build time and require no HTTP backend in desktop / offline
builds.

## Current Rule

### Locale codes

`vi-VN` (default) and `zh-CN` (canonical source-of-truth and fallback).
The closed allow-list lives in `shared/localization/types.ts`. Adding a
new locale requires (a) extending the `LocaleCode` union, (b) adding a
matching `locales/<code>.json`, and (c) updating the `LocaleSwitcher`
component options.

### Resolution chain

```
t(key, locale = "vi-VN")
   ├── if locale = vi-VN: return viBundle[key]
   ├── ELSE if locale = zh-CN: return zhBundle[key]
   ├── if vi missing → fall through to zh
   └── if zh missing → return marker(key)
                       (dev: "[!ns:key!]"; prod: raw key)
```

The `parseMissingKeyHandler` enforces step 4. A startup self-check calls
`t("__startup_self_check__:does.not.exist")` on both client and server
and refuses to mark the app ready unless the result is a non-empty
string. This satisfies AC 1.3.1.

### Namespace layout

Top-level namespaces live in `shared/localization/types.ts` as the
`NamespaceKey` union and the `NAMESPACE_KEYS` ordered list:

```
common         app shell, generic actions, generic errors
novel          novel/chapter/world editor surfaces
autoDirector   auto director cockpit + workflow
creativeHub    creative hub UI
knowledge      knowledge base UI
settings       settings UI (incl. LocaleSwitcher)
serverErrors   server-emitted error.code → message
serverLogs     server-emitted log lines surfaced to user
seedData       genres / story modes / style templates / anti-AI rules
```

Every locale bundle file MUST contain every namespace as a top-level
object even when empty. The coverage gate enforces this by structurally
walking the JSON.

### Glossary single-source rule

`shared/localization/glossary.json` is the canonical Chinese ↔
Vietnamese mapping for fiction-craft and product proper-noun terms. It
is loaded by:

- `scripts/i18n/translate-locale.mjs` — injected as a translation
  constraint into the LLM system prompt so machine translation honours
  canonical terms.
- `server/src/prompting/core/outputLanguage.ts` (Phase 5) — embedded
  into the AI Output Language Directive so generated novel content uses
  the same canonical Vietnamese terms.
- `scripts/i18n/verify-locale-coverage.mjs` — checked for `zh`
  uniqueness and craft-category `vi` uniqueness invariants.

Two `craft`-category entries cannot collapse to the same Vietnamese
term. Two non-craft entries can (e.g. `章` and `章节` both translate to
`chương` because they are linguistically equivalent in Vietnamese).

### Locale persistence

Client: `localStorage["ai-novel:locale"]`. Read at boot, written on
every locale switch. No automatic detection from `navigator.language` —
the user must pick via the Settings switcher (per AC 2.5 / 10.1).

Server: per-request resolution from the `Accept-Language` header
against the supported locale allow-list. Non-allow-list values fall
back to `DEFAULT_LOCALE`. Value attached to `res.locals.locale` by
`server/src/middleware/i18nMiddleware.ts`.

### Phasing

The translation work lands as six phase commits on
`feature/vietnamese-localization` per the design's phase plan. Each
phase commit must pass:

1. `pnpm typecheck` (exit 0)
2. `pnpm dev` boots without stderr error
3. `node scripts/i18n/verify-locale-coverage.mjs` (exit 0)
4. Phase-specific UI smoke surfaces look right in `vi-VN` and `zh-CN`

Phase 5 additionally includes an AI smoke test capturing 3 chapters of
output. Phase 6 additionally includes a verified `dev.db` backup.

## Examples

### Adding a new translatable string

1. Source: `<button>{t("common:actions.save")}</button>`
2. Run `node scripts/i18n/sync-locale-keys.mjs` to add the key to
   `zh-CN.json` with a `__TODO_ZH__:common:actions.save` placeholder.
3. Replace the placeholder with the canonical Chinese (`保存`).
4. Run `node scripts/i18n/translate-locale.mjs --target vi-VN` (Phase 2+)
   to populate the Vietnamese value (`Lưu`).
5. Run the coverage gate; it must pass.

### Translating a server error

1. Throw a typed error with a stable code, e.g.
   `new HttpError("novelNotFound", { status: 404 })`.
2. The `errorHandler` middleware looks up
   `t("serverErrors:novelNotFound", { lng: res.locals.locale })`.
3. Add the key to both bundles. The fallback chain handles the case
   where only `zh-CN` is filled in initially.

## Failure Modes

| Mode | Detection | Recovery |
|------|-----------|----------|
| Missing key in dev | UI shows `[!ns:key.path!]` | Add key to `zh-CN.json`, run translator. |
| Missing key in prod | UI shows raw key | Coverage gate must catch this before commit. |
| ICU placeholder mismatch | Coverage gate P3 fails | Fix the offending bundle; placeholders are part of the contract. |
| Glossary drift | Coverage gate P4 fails (duplicate craft `vi`) | Re-pick a canonical Vietnamese, OR move the offender to `ui` category if the duplicate is intentional (e.g. compound words). |
| Locale toggle drops state | PBT (Phase 2 task 2.6) catches this | Verify locale change does not unmount components or reset stores. |
| AI prompt produces mixed-language output | AI smoke test (Phase 5) | Iterate on the Output Language Directive; do NOT translate prompt instructions. |
| `Accept-Language` header injection | `resolveLocale` is closed over the allow-list (P5) | No mitigation needed; the property guarantees safety. |

## 动态服务端文本翻译策略

### 背景

服务端有四类字段会在运行时生成中文字符串，并直接序列化到 API 响应中展示给用户：

| 字段 | 来源 | 典型内容 |
|------|------|---------|
| `task.currentItemLabel` | 多个 service 在任务推进时写入，如 `DirectorCommandServiceHelpers.ts`、`NovelWorkflowApplicationService.ts`、`NovelWorkflowHealingService.ts` 等 | `"AI 正在生成书级方向候选"`、`"等待确认书级方向"` |
| `task.lastError` | 任务失败或心跳超时时由 watchdog / healing service 写入，如 `BookAnalysisWatchdogService.ts`、`NovelWorkflowHealingService.ts` | `"服务重启后任务已暂停，等待手动恢复。"`、`"任务心跳超时"` |
| `recentEvents[].summary` | `DirectorRuntimeStore.ts` 在节点完成/失败时拼接，如 `"${label}完成。"`、`"${label}失败：${error}"` | `"故事宏观规划完成。"`、`"章节细化失败：超时"` |
| `milestone.summary` | `autoDirectorFollowUpProjection.ts` 从 `milestonesJson` 解析，原始值由 `novelDirectorCandidateStage.ts` 等写入 | `"第一批 3 套书级方向已生成并完成每套书名组。"` |

这些字段的共同特征：
- 字符串在服务端**运行时**拼接，不是静态常量；
- 部分字段包含动态参数（章节序号、卷数、批次标签等）；
- 字段值直接写入数据库，再从数据库读出序列化到响应；
- 调用点分散在十余个 service 文件中，没有统一的序列化出口。

### 三种方案评估

#### 方案 (a)：迁移为 `code + params` 信封，读取时翻译

将所有写入点改为写入结构化信封：

```typescript
// 写入时
currentItemLabel: { code: "director.candidate.generating", params: {} }

// 读取时（API 序列化层）
t(`autoDirector:${label.code}`, { lng: locale, ...label.params })
```

**优点**：
- 翻译完全在读取侧完成，数据库中不存储任何语言相关内容；
- 支持未来多语言扩展，无需重新迁移数据；
- 参数化字符串（如章节序号）天然支持 ICU 格式。

**缺点**：
- 需要改动所有写入点（十余个 service 文件），blast radius 大；
- 需要为每条动态字符串定义稳定的 `code`，工作量大；
- 数据库中已有的历史记录（`lastError`、`checkpointSummary`）无法回填，需要兼容旧格式；
- 读取侧需要区分"旧格式字符串"和"新格式信封"，增加复杂度。

**结论**：适合 v2，不适合 v1 快速落地。

#### 方案 (b)：在 `taskFormatter` 中间件中服务端翻译后序列化

在 API 响应序列化层（task adapter 或专用 formatter）中，对这四个字段调用 `t()` 翻译后再输出：

```typescript
// 在 task adapter 序列化时
currentItemLabel: translateDynamicLabel(row.currentItemLabel, locale),
lastError: translateDynamicLabel(row.lastError, locale),
```

其中 `translateDynamicLabel` 先尝试精确匹配已知中文字符串到 `serverLogs` 命名空间的 key，匹配不到则原样返回（保底不丢失信息）。

**优点**：
- 写入点**零改动**，blast radius 最小；
- 翻译逻辑集中在一处，易于审计和扩展；
- 对已有历史数据无影响；
- 可以渐进式覆盖：先翻译高频字符串，再逐步补全。

**缺点**：
- 精确匹配方式对含动态参数的字符串（如 `"正在生成第 2 卷节奏板"`）覆盖率有限；
- 需要维护一份"已知中文字符串 → i18n key"的映射表；
- 动态拼接的字符串（如 `"${label}完成。"`）需要额外的模式匹配或正则提取。

**结论**：v1 推荐方案，blast radius 最低，可快速落地。

#### 方案 (c)：标记为"原始字段，可能含中文"，只翻译外层包装文本

保持这四个字段不变，只在前端 UI 的包装文本（标签、标题、按钮）上做翻译。

**优点**：实现成本最低。

**缺点**：用户在 vi-VN 模式下仍会看到中文内容，违反 Requirement 6.3（服务端用户可见字段必须翻译）。

**结论**：不满足需求，不采用。

### 决策

**v1 采用方案 (b)**，**v2 升级为方案 (a)**。

理由：
- v1 目标是以最小改动完成 Phase 4 的服务端翻译覆盖，方案 (b) 不需要改动任何写入点，只需在序列化层增加翻译调用；
- 方案 (b) 的覆盖率对于高频、固定的状态标签（`currentItemLabel`、`lastError` 的常见值）已经足够；
- 方案 (a) 的结构化信封设计更优雅，但需要协调十余个写入点，适合在 v2 中作为专项重构完成。

### v1 实施方案 (b) 的文件改动范围

需要改动的文件（仅序列化层，不改写入点）：

| 文件 | 改动内容 |
|------|---------|
| `server/src/services/task/adapters/NovelWorkflowTaskAdapter.ts` | 在序列化 `currentItemLabel`、`lastError` 时调用 `translateDynamicLabel(value, locale)` |
| `server/src/services/task/adapters/PipelineTaskAdapter.ts` | 同上 |
| `server/src/services/task/adapters/StyleExtractionTaskAdapter.ts` | 同上 |
| `server/src/services/task/adapters/KnowledgeTaskAdapter.ts` | 同上 |
| `server/src/services/task/adapters/ImageTaskAdapter.ts` | 同上 |
| `server/src/services/task/adapters/BookTaskAdapter.ts` | 同上 |
| `server/src/services/task/adapters/AgentRunTaskAdapter.ts` | 同上 |
| `server/src/services/task/autoDirectorFollowUps/autoDirectorFollowUpProjection.ts` | 在 `buildMilestones()` 序列化 `milestone.summary` 时翻译 |
| `server/src/services/novel/director/runtime/DirectorEventProjectionService.ts` | 在 `recentEvents` 映射时翻译 `item.summary` |
| `server/src/services/task/taskSupport.ts` | 新增 `translateDynamicLabel(value, locale)` 工具函数，内部查 `serverLogs` 命名空间 |
| `shared/localization/locales/zh-CN.json` | 在 `serverLogs` 命名空间下添加所有已知动态标签的 key |
| `shared/localization/locales/vi-VN.json` | 对应越南语翻译 |

`locale` 参数来源：各 adapter 已通过 `res.locals.locale`（由 `i18nMiddleware` 注入）获得请求级别的 locale，需要将其透传到 adapter 调用链。

### v2 升级路径（方案 a）

v2 将写入点迁移为结构化信封：

```typescript
// 新的写入格式
interface DynamicLabelEnvelope {
  code: string;           // 稳定的 i18n key，如 "director.candidate.generating"
  params?: Record<string, string | number>;  // ICU 参数
  fallback?: string;      // 兼容旧客户端的原始中文字符串
}
```

迁移步骤：
1. 在 `shared/types/task.ts` 中将 `currentItemLabel`、`lastError` 的类型扩展为 `string | DynamicLabelEnvelope`；
2. 逐个迁移写入点，将硬编码中文字符串替换为 `{ code, params }` 信封；
3. 在序列化层检测信封格式，优先用 `t(code, params)` 翻译，回退到 `fallback` 字符串；
4. 完成所有写入点迁移后，移除 `fallback` 字段和旧格式兼容逻辑。

`recentEvents[].summary` 和 `milestone.summary` 同理，但因为这两个字段的写入点更集中（分别在 `DirectorRuntimeStore.ts` 和 `autoDirectorFollowUpProjection.ts`），迁移成本更低，可以优先处理。

### 当前覆盖率说明

v1 方案 (b) 对以下类型的字符串覆盖率有限，需在 v2 中通过方案 (a) 补全：

- 含动态参数的字符串，如 `"正在生成第 ${volumeOrder} 卷节奏板"`；
- 由 LLM 生成后写入 `lastError` 的错误描述（这类字段已由 AI Output Language Directive 在 Phase 5 处理，不在本策略范围内）；
- `checkpointSummary` 字段（含书名、卷数等动态内容，建议在 v2 一并迁移）。
